# 근거 보완과 실행 과제 비교 — 2026-11-14~15 KST

이번에는 근거와 분류를 먼저 고친 뒤, 메모리가 없는 새 실행 환경에서 일반 웹 검색과 OpenAkashic 우선 검색을 비교했다. **현재 구성의 전반적인 품질·시간·토큰 개선은 입증되지 않았다.** 불리한 결과와 초기 실행 실패를 함께 보존한다.

## 반영한 자료 보완

인용 일치는 문장의 존재 확인이다. 그것만으로 전체 절차, 독립적인 사실 검증, 실제 업무 효과가 증명되지는 않는다. 편집자가 조합한 절차와 출처가 직접 설명하는 범위를 구분했다. 버전별 원래 인용과 과거 보고는 그대로 보존했다.

‘기타’ 19개는 기존 명시 태그에 따른 별칭 매핑 16개와 예제의 ‘조사·분석’ 태그 3개로 재분류해 0개가 됐다. 알려지지 않은 태그는 계속 ‘기타’다. 이 변경은 편집 분류이며 검증된 적용 가능성 온톨로지가 아니다. 이름·상황이 비슷하다는 이유로 방법이나 사용자를 병합하지 않았다. 손상된 옛 Streamlit 의견도 보존하고 별도의 새 설명만 추가했다.

## 비교 조건

SQLite WAL 백업, pandas 결측값 보고, Kubernetes probe 구성, HTTP JSON 클라이언트의 네 가지 실행 가능한 합성 업무를 각각 두 조건에서 한 번씩 수행했다. 실제 운영 DB나 고객 업무를 변경한 실험이 아니다. Kubernetes는 manifest 정적 검사이며 실제 클러스터에서 실행하지 않았다.

두 조건은 같은 gpt-6.1-sol, medium 추론, Codex 0.157.1, 새 Docker HOME을 사용했다. 후보에 기존 세션·메모리·저장소·인증 파일을 제공하지 않았다. 일반 조건은 native live web 검색으로 시작하고, OA 조건은 공개 아카이브 검색으로 시작한 뒤 필요하면 같은 native web와 일차 출처로 보완할 수 있었다. 과제·검사·모델·입력 자료·240초·12 provider 요청·200,000 token soft 중단 기준과 실행 순서를 미리 고정했다. 마지막 허용 요청이 soft 한도를 넘으면 그 실제 토큰도 모두 포함했다.

전체 성공은 프로세스 정상 종료, 고정 산출물 검사 통과, 품질 네 항목 모두 1점 이상, 중대한 무근거 주장 없음, 검색 경로 준수를 함께 요구한다. 코드 검사와 정상 완료는 다르게 집계했다. 품질은 정확성/근거 적합성/한계 설명/산출물 사용성을 각 0~2점으로 별도 모델 평가했다. 평가자는 식별 키·시간·토큰·checker를 보지 않았지만 README에 검색 경로 단서가 남아 **완전한 맹검은 아니다**. 동일 모델 계열의 단일 평가이며 전문가·실사용자 평가를 대신하지 않는다.

### 자료를 찾은 경우와 찾지 못한 경우

정확한 방법을 실제 적용한 것은 SQLite OA 시도다. method_5af91cc7219a4130a3a2cf2d7630b031 v2의 완전한 본문을 읽고 백업·재열기·검사 절차를 구현했다. 일반 웹 대비 토큰은 226,740→204,787로 9.68% 적었지만 시간은 219.06→234.26초로 6.94% 길었고, 두 후보 모두 자원 한도 안에서 최종 작업을 완료하지 못했다. OA 산출물에는 README가 없었다. 이 한 쌍을 같은 품질에서 효율이 좋아졌다는 증거로 쓰지 않는다.

Kubernetes에는 관련 방법 대신 TanStack Query 방법이 추천됐고, 추가 검색에서는 결과가 없었다. 후보는 이를 적용하지 않고 공식 Kubernetes 문서로 넘어갔다. pandas는 bundle이 비어 있어 공식 문서로 보완했다. HTTP에도 부적합한 TanStack 방법이 전달됐고 OA 후보는 구현 없이 시간 초과됐다. 이들을 기존 노하우의 적용 성공·실패로 꾸며 연결하지 않는다. 과제 네 개 모두 맞는 방법이 제공된 비교가 아니며, 위 분류는 결과 로그를 본 뒤 작성한 진단이다. 원래 여덟 행의 분모나 채점 기준은 바꾸지 않았다.

Kubernetes는 OA 우선이 약 10.99% 빨랐지만 토큰은 약 7.82% 많았다. pandas는 시간 약 13.64%, 토큰 약 29.41%가 늘었다. 토큰이 모두 있는 세 쌍만 합치면 567,847→604,685로 6.49% 많았다. 실패한 시도도 포함하는 사후 부분집합 소계이며 전체 비용이나 성공당 효율을 뜻하지 않는다. HTTP OA의 전체 usage가 없어 전체 토큰 차이는 **null**이다.

### 사용량과 실패의 경계

토큰은 broker에 기록된 provider input/output usage 카운터다. cached input은 input에 이미 포함되므로 다시 더하지 않는다. 브로커가 response ID와 원본 응답 스트림 해시를 저장하지 않았기 때문에 완전히 독립된 청구 원장으로 식별 검증한 값은 아니다. 시간 초과 시도에는 마지막 영수증이 없어 알려진 소계만 남기고 총량을 추정하지 않았다. native web의 별도 비용과 준비·근거 보완·색인·평가 비용은 후보 시간/usage에 합치지 않았다. 금액 절감 주장은 하지 않는다.

초기 v2의 16예정 중 첫 시도는 모델 호출 전 격리 경로 접근 오류로 끝났고 15개는 미실행이었다. 이를 고친 v3는 100k soft 기준에서 16예정 중 6개 finalized, 1개 시작 후 미완료, 9개 미실행으로 중단했다. v3의 여섯 프로세스는 모두 exit1이었고 검사만 3/6 통과했다. 이후 200k·한 번 반복으로 자원을 보정한 v4를 별도 코호트로 실행했다. v2/v3 실패와 미실행을 지우거나 v4 성과와 합치지 않았다. 200k는 보편적인 최적 예산이 아니다.

## 다음 변경의 기준

현재 병목은 자료 수보다 관련 방법 회수 실패, 부적합 후보, 중복 전체 본문 조회, 코드 작성 뒤 문서·최종 응답 미완료다. 에이전트 가이드는 완전 bundle을 이미 받았다면 같은 본문을 다시 GET하지 않고 필요한 정보의 공백만 추가 확인하도록 바꿨다. 이 안내 변경은 이번에 동결한 프롬프트에 소급 적용하지 않았으며 토큰 절감 효과를 별도로 측정하지 않았다.

후속 실험은 이번 과제·정답에 검색 임계값을 맞추는 대신, 관련 방법이 실제 있는지 사전 확인한 새로운 과제에서 검색 성공과 적용 효과를 분리해야 한다. 현재 결과를 효율적인 서비스의 입증으로 홍보하지 않는다. 적용·재현·정정 기록은 정확한 방법 버전에 연결하며, 운영 데이터가 늘어났다는 사실을 품질 향상으로 환산하지 않는다.

동결 과제·검사·생성 코드·판정·해시와 재검사 방법은 [공개 재현 자료](../benchmarks/practical-comparison-20261114/README.md)에 보관한다. 원시 provider trace, 시스템 프롬프트, 인증·환경 파일, 전체 출처 본문은 공개하지 않는다. 합성 생성 코드는 실제 서비스에 바로 적용할 코드가 아니라 검토 대상이다.


## 실제 적용·반례·수정을 어떻게 남겼는가

비교 종료 뒤 소유자 전용 API로 다음 기록을 발행하고 같은 요청의 멱등 재시도 및 공개 재조회를 확인했다. 과거 보고의 버전이나 원문을 바꾸지 않았다.

- SQLite v2 과제 적용: `outcome_5606a036d7d74c8995ab2587187ebd1b`. 실제 백업 코드와 자체 검사·고정 checker는 통과했으나 README·최종 응답 없이 자원 한도로 종료한 **partial** 보고다.
- SQLite v2의 시점 설명 반례: `outcome_eb439c2bff3d41669ed891f828b78d50`. 모델 비교와 별도의 운영자 합성 fixture에서 4페이지 복사 후 다른 연결의 한 행 commit이 사본에 포함됐다. 백업 자체는 유효했지만 무조건 시작 시점에 고정된다는 설명에는 반례가 있었다.
- 같은 방법의 v3: 이 반례 보고를 정확히 연결한 정정이다. 증분 복사 중 재시작 가능성을 명시하고, 백업 전에 기준 시점·동시성 조건을 정하며 동일 시점이나 고정된 읽기 범위가 보장된 경우에만 원본과 행 일치를 요구하도록 절차와 성공 기준도 함께 고쳤다. 계속 변하는 현재 원본과의 차이만으로 백업 실패를 확정하지 않는다.
- SQLite v3 재확인: `outcome_e10b3f2302bd49e49e313f89fe6f52d7`. 같은 코드로 새 fixture를 한 번 더 실행해 12개 검사와 독립 재열기·512행 비교·cleanup을 확인했다. 이는 조건부 설명과 관찰이 그 범위에서 일치한다는 **partial** 보고이며 모든 동시성·특정 시점·운영 복구 보장은 검증하지 않았다.
- 검색 한계 의견 세 개: Kubernetes와 HTTP의 부적합 TanStack 추천, pandas의 빈 bundle을 각각 남겼다. 절차를 적용하지 않은 방법에 알고리즘 실패 outcome을 붙이지 않았다.

이력은 [현재 SQLite 방법 API](https://knowledge.openakashic.com/research/api/methods/method_5af91cc7219a4130a3a2cf2d7630b031)와 [v2 원문](https://knowledge.openakashic.com/research/api/methods/method_5af91cc7219a4130a3a2cf2d7630b031/versions/2)에서 읽을 수 있다. 그래프는 정정 노드가 `addresses`로 원래 partial 보고를, `implemented_by`로 v3를 잇는다. 새 버전으로 원래 보고의 귀속을 옮기지 않는다. 공개 화면은 읽기 전용이고 수정은 계속 소유자의 비공개 API에서만 가능하다.

별도 fixture의 코드·원본 v2/v3 스냅샷·진행 값·검사 결과와 SHA는 [시점 반례 재현 자료](../benchmarks/sqlite-temporal-boundary-20261115/README.md)에 있다. v2와 v3에서 remaining 510→513과 이후 commit 포함을 관찰했고, 두 통제 사례의 사본 무결성과 전체 행 비교를 확인했다. v3는 설명을 정밀화한 것이며 백업 알고리즘 성능 향상을 측정한 변경이 아니다. 공식 [SQLite backup API](https://www.sqlite.org/c3ref/backup_finish.html)의 다른 연결 쓰기와 재시작 설명도 함께 참조했다.

수정된 현재 61개 방법의 의미 색인은 stale/missing 0으로 재확인했다. **위 비교 수치는 수정 전 동결된 61개 v2 자료의 결과**다. 이후 v3 정정·재확인을 새 토큰 절감이나 품질 개선 수치로 소급 계산하지 않는다.
