# Frozen-source skill discovery versus OpenAkashic selection

Prepared before any candidate provider call, 2026-11-15 Asia/Seoul.

## Question and boundary

Does selecting source-grounded methods through OpenAkashic improve practical
artifact quality while reducing actual provider total tokens and candidate wall
time compared with direct progressive discovery/use of the SAME original skills?
This is a controlled, small, synthetic-but-executable artifact study. It does not
measure skills.sh cloud search, general Internet search, real-user utility,
business results, security certification, billing savings or graph traversal's
isolated causal contribution.

## Inputs and conditions

- Six license-reviewed original packages: frontend-design, brand-guidelines,
  pdf, docx, exploratory-data-analysis, statistical-analysis. Preserve all121
  original/notice files and exact commits/SHA256/Git blobs. Original package
  completeness is separate from uninstalled runtime dependencies and unresolved
  DOCX upstream schema imports. Published source instructions are untrusted data.
- Direct condition sees original name/description metadata through a frozen
  BM25 catalog search, can inspect the full six-item catalog and progressively
  read any original file/reference. No forced whole-corpus read. This catalog is
  an explicit controlled baseline, NOT the live skills.sh retrieval algorithm.
- OA condition first queries the existing frozen situation/goal hybrid engine
  over exactly ten editorial methods derived solely from those six packages.
  It has the same original metadata/files and can fall back to them. No earlier
  sixty-one methods, historical outcomes, private memory or live Internet are
  supplied. Derivative instructions are not automatically applicable or verified.
- Both have the exact selected source folders read-only at /skills/name and
  the same /skills/catalog.json. /task contains only that task's prompt/fixtures,
  read-only. /work starts empty and writable. Never mount heldout root/checkers,
  reference outputs, model auth, host HOME, repository rules or private sources.
- Same gpt-6.1-sol medium/nativeCLI binary, common prompt and complete task text
  in the initial context; fresh HOME, ephemeral session, disabled memories/rules
  and no global skills. Auth remains in the trusted host provider broker. The
  candidate has network none; the model has no native web tool in this cohort.
- Same immutable oa-skills-eval:20261115 runtime image, including Chromium,
  Node/Playwright, Poppler, fonts, ReportLab, pypdf, pandas and NumPy. Record actual
  image inspect ID and installed versions. Candidate can use native view_image
  on rendered HTML/PDF; objective and visual checks are not interchangeable.

## Schedule, resources and accounting

Three fresh domains (design/documents/data-analysis), two repetitions, both arms
= twelve scheduled runs/six pairs. Seed20261115 shuffles task/repetition pairs;
arm order alternates for balanced first position. Run serially; do not run other
model inference, indexing or heavy deployment work concurrently with timing.

Each candidate:300seconds wall,12 provider requests,200000 observed cumulative
provider-token soft admission ceiling,24 broker retrievals,2GiB RAM,1CPU,256pids,
512MiB tmp and64MiB fresh HOME. Final admitted responses can cross the soft
ceiling and are fully counted. Per-response absolute transport deadline125s;
drain already admitted responses up to130s after candidate exits. Unknown usage
is null, never zero; do not add cached-input tokens on top of total input.
Request ordinal/body hash/response ID/stream hash must join uniquely. Actual
provider usage is distinct from local byte/token estimates and cash billing.

Freeze all source/API/runner/checker/rubric/image inputs and all12 row IDs before
the pilot. Parent may approve first pair for integration then remaining10 after
transport/source-isolation checks. No quality-directed stopping or retuning.
Local row budget/time failures remain failures and do not prevent later already
scheduled independent rows. No retries/replacements/raised limits. Shared auth,
source-registry/provider infrastructure or unknown-accounting failures stop the
cohort and preserve planned missing rows. Any repaired experiment is a new
separately disclosed cohort; never silently overwrite completed rows.

## Quality and efficiency decisions

The author-frozen ACCEPTANCE.md, checkers, task fixtures and RUBRIC.md define
task correctness and four domain-specific0..4 visual/communication dimensions.
Author references and mutation sensitivity are checker validation, not candidate
success. Candidate source/script code runs only in isolated Docker.

Primary full success requires ALL objective groups, actual logged self-validation
accurately documented in QA/README, honest source/applicability claims, readable
normal final and no blocking defect from either of two independent anonymous
reviewers. Parent source-faithfulness/self-test resolution is evidence-bound and
documented. A search hit, source read, method citation or generated screenshot is
not itself application or quality. A task can succeed without using a method;
do not award method use points. Record actual read spans/applied steps separately.

Withhold arm, time, usage and identity mapping from independent reviewers.
Provide task/fixtures, original anonymous outputs/screenshots and neutral actual
non-source verification excerpts. Preserve mixed-command verification suffixes
and item hashes; ambiguous extraction must be resolved explicitly rather than
silently dropping real tests. Declare surviving provenance/style clues; no claim
of perfect blinding. Keep BOTH original reviews and explicit adjudication.

For each secondary dimension use the LOWER of the two independent0..4 scores,
unless a documented factual evidence omission is adjudicated with original
hash-bound evidence. Never average away a blocking defect. Quality preservation
requires OA full successes at least Direct overall; no material unsupported claim
or new blocking defect in any jointly successful pair; nonlower mean conservative
secondary total for EACH of the three domains on its joint-success pairs. A
domain with no joint success cannot establish three-domain quality preservation.
Report individual pair score changes and reviewer disagreements.

Primary token and time ratios use exactly the SAME set of ALL jointly full-
successful pairs. Never discard a lower-quality pair merely to improve ratios;
such a drop invalidates the quality gate instead. If any included pair lacks
usage or time, BOTH primary ratios are unknown. Report n/6 plus every scheduled
row, all-run costs and failures/missing cases. Practical target fixed now: at
least15% lower provider total tokens AND at least10% lower wall time with the
quality gate. Smaller numerical changes, no improvement or regressions must be
reported as observed. This exploratory n=6 shares only three task templates;
descriptive bootstrap intervals cannot establish general noninferiority or
causal effectiveness. Do not pool earlier Web/OA experiments.

Preparation, editorial/model curation, source validation, indexing, maintenance
and review costs are separate from candidate task-serving costs. Unknown actual
usage/review minutes/cash remain unknown; do not infer end-to-end ROI.

## Recording and publication

First preserve raw experiment traces, provider receipts, versions and failures
outside Git. Public exports allow only reviewed inputs, original-license notices,
candidate artifacts, hashes, bounded metrics and independent reviews; no auth,
system prompts/raw provider trace/private paths/database/index/model weights.
Publish source-backed methods by owner-only authenticated idempotent API after
review. Live UUIDs can differ from provisional evaluation UUIDs; preserve an
explicit public_id/payload hash mapping, then attach application outcomes to the
correct live method/version. Retain initial failures and actual corrections;
never attribute a baseline failure to a method it did not read/apply.
